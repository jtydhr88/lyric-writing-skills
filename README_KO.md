# lyric-writing-skills（작사 스킬 모음）

[English](README.md) · [中文版](README_ZH.md) · [日本語](README_JA.md) · 한국어

노래 가사를 쓰기 위한 18개의 agent skill（[Claude Code](https://docs.anthropic.com/en/docs/claude-code/skills) 와 [OpenAI Codex](https://developers.openai.com/codex/) 용）. 네 개 언어로 된 29권의 책——영어 작사 교본, 중국어 시율과 작사, 광둥어 실무, 한국어 음성학——에 손드하임이 직접 주석을 단 가사 전집 두 권을 더해 뽑아낸 것입니다.

`SKILL.md` 는 공개 규격 [agentskills.io](https://agentskills.io) 를 따르며 두 agent 가 같은 파일을 공유합니다. 한 번 설치하면 양쪽에서 모두 동작합니다.

**결과물은 가사만이 아니라 한 장의 사양서입니다.** 가사를 요청하면 agent 는 LYR-SPEC 을 채웁니다——이 노래가 말하는 단 한 가지, 누구에게 하는 말인지, 어느 순간의 이야기인지, 곡 전체를 관통하는 사물 하나, 각 행의 음절 수와 강세 위치, 압운 방식, 의도한 비대칭, 그리고 언어층 점검 결과——그런 다음 그것을 생성 백엔드의 입력으로 컴파일합니다. 초고를 고칠 때 대조하는 것도 바로 같은 문서입니다.

**이 라이브러리의 전제를 그대로 적습니다.** AI 가 쓴 가사는 단어를 못 고른 것이 아닙니다. **아무도 선택을 하지 않은** 것입니다. 문법은 완벽하고 압운도 가지런하며 이미지도 풍부한 네 개의 절——그런데 그 네 절은 어느 노래에 붙여도 말이 됩니다. 기계가 썼다는 것이 한 번에 들리는 이유가 바로 그것입니다. 이 라이브러리의 모든 관문은 실제 선택을 하나씩 강제로 끌어내기 위해 존재합니다.

**자기 언어로 물어보세요.** skill 본문은 중국어로 쓰여 있습니다. 저본의 대부분이 중국어 원저이거나 중국어 번역본이기 때문입니다. 어떤 언어로 묻든 agent 는 그 언어로 답합니다.

**이 스킬은 생성 모델을 빠르게 만들지 않습니다. 시간을 들여 품질을 얻는 방식입니다.** 전문 음악 작업 워크플로를 한 번 온전히 돌리면 한 곡에 20분 이상 걸리는 일도 흔합니다(agent가 판단 기준을 읽고, 규격서를 채우고, 자체 점검을 거치기 때문입니다). 그 대가로 얻는 것은 몇 줄의 프롬프트가 아니라 전문가 수준의 규격서입니다.

**이 라이브러리는 어떤 작품도 담고 있지 않습니다. 저자 본인의 것도, 다른 가수의 것도, 편곡도 가사도 없습니다.** 음악 작품의 좋고 나쁨은 주관적인 판단입니다. 직접 써 보고, 이 도구의 가치와 시간이라는 비용을 스스로 판단해 주십시오.

## 이 시리즈의 네 라이브러리

하나의 오디오 라인을 독립된 네 라이브러리로 나누었습니다. 각각 단독으로 쓸 수 있고, 이음새가 문서화되어 있어 조합해서도 씁니다.

| 라이브러리 | 하는 일 | 상태 |
|---|---|---|
| **[music-composition-skills](https://github.com/jtydhr88/music-composition-skills)** | 작곡과 편곡. 브리프를 ARR-SPEC으로 바꿉니다: 조, 템포, 섹션 표, 화성, 누가 언제 들어오고 나가는지, 에너지 곡선, 보컬과 믹스 의도. Suno, YuE2, MIDI용 입력으로 컴파일 | 공개됨 |
| **[lyric-writing-skills](https://github.com/jtydhr88/lyric-writing-skills)** | 작사. 입의(立意) 관문을 LYR-SPEC으로 바꿉니다: 구조, 이미지, 운, 서술, 그리고 중국어(보통화·광둥어), 영어, 일본어, 한국어의 언어 층 | **이 라이브러리** |
| **영화 음악** | 영상에 맞춰 쓰는 음악: 스포팅, 컷과의 관계, cue를 쓰고 이름 짓는 법, 테마가 영화 전체에서 발전하는 방식 | 예정 |
| **믹싱과 사운드 디자인** | 믹스 의도를 실제 조작으로 바꾸기: EQ, 컴프레션, 리버브, 오토메이션, 마스터링 | 예정 |

**독립적입니다.** 기존 멜로디에 가사를 붙이려면 작사 라이브러리만 있으면 됩니다. 연주곡을 편곡하려면 작편곡 라이브러리만 있으면 됩니다.

**이름 붙은 인계로 조합됩니다.** ARR-SPEC과 LYR-SPEC은 양방향입니다. 곡이 먼저면 섹션 표와 마디 수를 넘기고, 가사가 먼저면 행 길이와 강세 위치를 돌려주며, 여섯 필드는 양방향에서 일치해야 합니다. ARR-SPEC 안의 `mix_intent`는 믹싱 라이브러리가 브리프로 받는 것이고, 영화 음악 라이브러리의 cue sheet는 작편곡 라이브러리가 브리프로 받는 것입니다.

**이음새는 이미 쓰여 있습니다.** 모든 스킬이 경계 표를 갖고 있어, 다른 라이브러리에 속한 질문은 그 자리에서 어설프게 답하지 않고 이름으로 넘깁니다. 그래서 예정된 두 라이브러리가 이미 곳곳에서 언급됩니다: EQ와 컴프레션 실무는 믹싱 라이브러리로, 스포팅과 cue 작성은 영화 음악 라이브러리로.

## 생성 모델이 있는데 왜 이것이 필요한가

언어 모델은 10초면 네 개의 절을 써 줍니다. 운도 맞고 자수도 가지런하며 이미지도 풍부합니다. 문제는 이 라이브러리 전체가 바로 그것을 위해 만들어진 그 한 가지입니다 —— 그 네 절은 어느 노래에 붙여도 말이 됩니다.

모델은 당신이 정하지 않은 자리를 전부 메웁니다. 그리고 메우는 값은 그것이 읽어 온 모든 것의 평균입니다. 사람들이 "기계가 썼다"고 알아듣는 것이 바로 그것입니다. 구체적인 사물이 놓여야 할 자리에 추상명사가 놓이고, 네 단락의 길이가 똑같고, 후렴이 세 번 다 글자 하나 다르지 않고, 감정의 호가 아픔에서 받아들임으로, 다시 축복으로 말끔하게 해소되고, 각운은 언제나 누구나 가장 먼저 떠올릴 그 단어입니다. 이것은 글이 나쁜 것이 아닙니다. **아무도 선택을 하지 않은 소리**입니다.

이 skill 모음이 공급하는 것이 바로 그 선택들입니다. 현역 작사가가 내릴 만한 수준으로 정하고, 나중에 대조할 수 있는 자리에 적어 둡니다 —— 이 노래가 말하는 단 한 가지, 누구에게 하는 말인지, 몇 분의 어느 순간에 하는 말인지, 되풀이 나오면서 나올 때마다 뜻이 달라지는 사물은 무엇인지, 어느 한 행이 형식을 깨고 왜 깨는지, 어느 글자가 그 음에 앉으면 안 되는지（성조가 바뀌어 다른 단어가 되어 버리므로）. **하는 일은 전문가 수준의 규칙으로 생성 모델을 지휘하는 것입니다. 생성 모델을 다시 만들려는 것이 아닙니다.**

중국어 가사에는 두 번째 이유가 있고, 이것은 취향의 문제가 아닙니다. 표준중국어에서는 성조와 선율이 충돌하면 듣는 사람에게 다른 단어로 들립니다. 광둥어에서는 그냥 다른 단어입니다. 성조를 확인하지 않고 문장만 예쁘게 쓰는 모델은 부르는 순간 무너지는 가사를 내놓습니다. 이런 제약은 계산할 수 있는 것이고, 이 라이브러리는 그것을 적어 둔 곳입니다. 한국어에서 이에 해당하는 계산 가능한 제약은 받침이 노래 부르기에 미치는 영향입니다 —— 다만 **이 패키지에는 한국어 층이 없습니다**（아래 「이 패키지에 들어 있지 않은 것」 참조）.

모델은 여전히 가수이고 녹음실입니다. 이것은 거기에 건네는 가사 원고이며, 자리마다 그렇게 한 이유가 붙어 있습니다.

## 설치

### Claude Code

#### 플러그인 마켓플레이스（권장）

```
/plugin marketplace add jtydhr88/lyric-writing-skills
/plugin install lyric-writing@lyric-writing-skills
```

이후에는 `/lyric-writing:<skill>` 로 호출합니다. 예: `/lyric-writing:lw-workflow`.

#### 개인 단위（모든 프로젝트）

```bash
git clone https://github.com/jtydhr88/lyric-writing-skills.git
cp -r lyric-writing-skills/plugins/lyric-writing/skills/* ~/.claude/skills/
```

#### 프로젝트 단위

```bash
mkdir -p .claude/skills
cp -r lyric-writing-skills/plugins/lyric-writing/skills/* .claude/skills/
```

### Codex（CLI / ChatGPT 데스크톱 앱 / IDE 확장）

```bash
codex plugin marketplace add jtydhr88/lyric-writing-skills
# Then: Plugins → select "Lyric Writing Skills" → Install
```

또는 같은 파일들을 `~/.agents/skills/`（개인 단위）나 `.agents/skills/`（프로젝트 단위）에 복사하면 됩니다.

#### 확인

agent 는 관련 맥락을 감지하면 자동으로 불러옵니다. 목록을 보려면 `/skills`.

## 사용 예

```
# "이 멜로디에 가사를 붙여줘 —— 마디 수와 행마다 들어갈 음절 수는 여기 있어"
# → lw-workflow（곡 먼저 트랙）→ lw-song-intent → lw-structure → lw-mandarin

# "이 원고, 읽기엔 멀쩡한데 뻔하다. 어디가 문제인지 말을 못 하겠어"
# → lw-ai-tell-audit: 열거 가능한 여덟 가지 기계 지문, 각 항목을 담당 skill 로 넘김

# "광둥어 멜로디에 가사를 채워줘"
# → lw-cantonese: 먼저 음높이 부류 체계로 계산하고 그다음에 글자를 고른다 ——
#   광둥어는 쓰는 순서가 거꾸로이며 다른 어떤 언어층으로도 대체되지 않는다

# "이 벌스를 랩으로 바꿔줘"
# → lw-rap（압운 밀도, 다음절 압운, 중국어 랩 전용 대응표）

# "이 행을 부르면 내가 쓴 그 말로 들리나, 아니면 다른 말로 들리나?"
# → lw-tone-check: 각 단락의 최고음, 각 행의 첫 글자, 큰 도약의 착지점만 본다
#   —— 전체 글자의 약 5분의 1
```

## 자주 쓰는 조합

겉보기보다 복잡합니다. 한 줄짜리 brief가 작곡·편곡·작사 세 방면에서 십여 개 skill을 움직이고, 에이전트가 무엇을 읽고 무엇을 내놓는지는 그 한 줄에 핵심 항목 몇 가지가 들어 있는지로 정해집니다. 아래는 실제로 끝까지 돌려 본 조합입니다. 어떻게 말하는지, 어느 skill을 지나는지, 무엇이 나오는지. 가사가 있는 용례는 작곡편곡 라이브러리와 작사 라이브러리를 둘 다 설치해야 합니다.

**1. 특정 가수의 스타일로 가사 있는 곡 쓰기**(가장 흔함)

> 어떤 가수의 어떤 곡 같은 스타일의 중국어 팝 한 곡, 여성 보컬, Suno로 생성, 가사 포함.

지남: lw-workflow → lw-song-intent → lw-structure → lw-mandarin → lw-tone-check → lw-suno-interface; mc-workflow → mc-style-chinese-pop → mc-melody → mc-development → mc-arrangement-arch → mc-vocal-direction → mc-render-compile
산출: LYR-SPEC.yaml, ARR-SPEC.yaml, suno-pack.md(제목, 스타일 설명, 섹션 태그 붙은 가사, 제외어)
비고: 참조 가수에게서 빌리는 것은 편성·템포·보컬 페르소나·섹션 진행뿐입니다. 가사와 멜로디는 빌리지 않습니다.

**2. 抖音용 중독성 있는 곡, 서사 없이**

> 抖音용 중독성 있는 곡 한 곡, 여성, 달콤하게, 서사는 없이. Suno 생성, 가사 포함.

지남: lw-song-intent(태도형) → lw-structure(반복 예산, 훅 위치) → lw-rhyme → lw-mandarin; mc-style-chinese-pop → mc-rhythm-groove → mc-arrangement-arch → mc-render-compile
비고: "서사는 없이" 한마디가 가사 유형을 정합니다. 말하지 않으면 기본값은 정경형입니다.

**3. 슬픈 사랑 노래, 직접 말하기, 장면 없이**

> 어떤 가수의 어떤 곡 같은 슬픈 사랑 노래, 남성 보컬, Suno 생성, 가사 포함. 직접 말하는 쪽으로, 장면 묘사는 없이.

지남: 1과 같되 lw-song-intent가 태도형으로 가고, 닻은 물건이 아니라 한 문장(후렴마다 첫머리에 반복되는 행); mc-vocal-direction이 온마이크 남성 보컬과 마지막 한 줄의 여백을 맡음
비고: 코퍼스에서 태도형 곡의 열에 넷은 사진으로 찍을 수 있는 물건이 하나도 없습니다. 후렴은 "너"에게 하는 한 문장, 벌스는 나의 상태, 첫 줄은 독백. 이걸 원하면 brief에 "직접 말해, 장면도 물건도 없이"라고 씁니다.

**4. 하나의 기분, 이야기로 만들지 않기**

> 중국어 팝 한 곡, 3분 30초, 여성 보컬. 주제는 이사하던 날 충전 케이블을 벽 콘센트에 꽂아 둔 채 나와서 두 블록을 걷고서야 생각났는데 돌아가지 않은 것. 이야기로 쓰지 말고, 생각났다가 그냥 두는 그 기분을 원해.

지남: lw-song-intent(정경형, 닻 물건은 케이블) → lw-imagery → lw-structure → lw-mandarin → lw-tone-check; 곡 쪽은 1과 같음
비고: 정경형과 서사형의 경계가 여기입니다. 물건은 있고, 줄거리는 진행하지 않습니다.

**5. 연주곡, 처음부터 작곡**

> 2분 40초짜리 연주곡, 쇼트 영상 배경용. 주선율은 나일론 현 기타, 약간의 타악과 베이스, 건반 한 대까지 허용. 느낌은 "오후 세 시, 누군가를 기다리는데, 급하지 않다". 보컬 없음.

지남: mc-workflow → mc-development(동기, 성격, 전개 수법) → mc-melody → mc-form → mc-harmony → mc-rhythm-section → mc-orchestration → mc-render-compile
산출: ARR-SPEC.yaml(material 블록과 섹션별 development 채움), suno-pack.md, 한 쪽짜리 설명
비고: 가사가 없으므로 작사 라이브러리는 관여하지 않습니다. 판정 기준은 mc-development에 있습니다. 새 재료는 절반 미만, 재현 있음.

**6. 가사와 멜로디는 있고, 편곡만**

> 멜로디와 가사가 이미 있는 중국어 사랑 노래를 편곡해 줘. 살사 느낌, 브라스 포함, 중간보다 조금 빠르게. 사양서만, Suno 프롬프트는 필요 없음.

지남: mc-workflow(편곡 경로) → mc-style-latin → mc-rhythm-section → mc-orchestration(브라스) → mc-arrangement-arch → mc-texture-layering
산출: ARR-SPEC.yaml과 한 쪽짜리 설명뿐

**7. 융합: 벌스는 랩, 후렴은 중국풍**

> 어떤 곡 같은 랩 더하기 중국풍 곡, 완전한 중국어 가사, Suno용.

지남: mc-workflow §2.4 스타일 융합 → mc-style-hiphop(베이스) + mc-style-chinese-pop(오버레이); lw-rap(벌스) + lw-chinese-style(후렴) + lw-mandarin

**8. 광둥어 가사를 주어진 멜로디에**

> 이 멜로디에 광둥어 가사를 붙여 줘. 마디 수와 행마다 음절 수는 첨부.

지남: lw-workflow(곡 먼저) → lw-cantonese(먼저 음높이 부류로 계산, 그다음 글자 선택) → lw-tone-check
비고: 광둥어는 쓰는 순서가 거꾸로이며 표준중국어 층으로 대체할 수 없습니다.

**9. Suno 대신 로컬 오픈소스 모델(YuE2)**

> 같은 곡을 Suno 없이 로컬 YuE2로 생성하고 싶어. 사양서를 ABC 악보로 컴파일해 줘.

지남: 1과 같고, 여기에 mc-symbolic-score(ARR-SPEC을 ABC로 컴파일, 보컬 라인은 소문자 음이름 음역에, w: 가사 행 포함)
비고: 실험 단계입니다. 가사가 불려서 들리는 비율은 스타일과 가사를 직접 넘기는 방식보다 아직 낮습니다. 자세한 내용은 mc-symbolic-score §6b.

brief 안에서 실제로 작동하는 문장들:

| 당신이 말하는 것 | 그것이 정하는 것 |
|---|---|
| 가수 이름 + 곡 제목 | 편성·템포·보컬 페르소나·섹션 진행을 빌림. 가사와 멜로디는 빌리지 않음 |
| 여성/남성, 달콤/온마이크 | mc-vocal-direction의 페르소나와 음역 |
| Suno / 로컬 YuE2 / 사양서만 | 출구: suno-pack, ABC 악보, ARR-SPEC만 |
| 서사 없이 / 직접 말하고 장면 없이 / 이야기로 만들지 않기 | 가사 유형: 태도형 / 물건 없는 태도형 / 정경형. 말하지 않으면 기본은 정경형 |
| 길이 | 섹션 수와 마디 수를 여기서 역산 |
| 산출물 목록 | 원하는 파일을 적으면 에이전트는 그 목록대로 냄. 하나라도 빠지면 미완 |

## 도구는 전혀 필요 없습니다

이 플러그인은 순수한 텍스트입니다. 돌릴 스크립트도 없고 Python 도 Node 도 필요 없으며 lint 단계도 없습니다. LYR-LINT 열 개 항목은 모두 눈으로 판정할 수 있고, 성조와 선율의 충돌 점검에도 손으로 하는 방법이 있어 문제가 실제로 생기는 세 종류의 위치만 봅니다.

**규칙은 판단 기준이지 반드시 통과해야 하는 관문이 아닙니다.** 어떤 항목이 통과하지 못하면 그 행을 고치거나, 왜 이 노래는 그래야 하는지를 한 문장으로 쓰거나 둘 중 하나입니다.

## 다국어 지원

**소스는 한 벌, 언어는 실행 시점에 나옵니다.** skill 은 중국어로 딱 한 번 쓰여 있고, 어떤 언어로 묻든 agent 는 그 언어로 답합니다. 켜고 끄는 플래그도, 따로 하는 설치도, 언어별 플러그인도 없습니다.

**여기서는 두 가지를 갈라 놓고 말해야 합니다.** 이 라이브러리에는 **언어층**이 있어서 둘이 섞이기 쉽기 때문입니다. 언어층이 다루는 것은 **가사**를 어떤 언어로 쓰느냐입니다 —— 표준중국어의 성조, 광둥어의 협음, 영어의 강세, 일본어의 모라. 아래 방침이 다루는 것은 **지시 파일**이 어떤 언어로 쓰여 있느냐입니다. 일본 작사가가 일본어로 물으면 일본어 답변과 `lw-japanese` 층 전체를 받습니다. 그 뒤에 있는 지시 파일이 중국어일 뿐입니다.

한국어의 경우에는 두 가지가 동시에 성립하며, 둘을 섞으면 안 됩니다. 첫째, 지시 파일은 중국어입니다——이것은 위에서 말한 정책의 문제입니다. 둘째, **이 패키지에는 한국어 층 자체가 없습니다**——이것은 저본의 문제이며 위의 「이 패키지에 들어 있지 않은 것」에 적어 둔 그대로입니다. 한국어로 물으면 한국어로 답이 오지만, 그 답 뒤에 받침과 노래를 다루는 언어층이 서 있는 것은 아닙니다.

skill 본문을 다른 언어로 갈라내지는 않습니다. 이것은 빠뜨린 것이 아니라 내린 결정입니다. 자매 프로젝트 [screenwriting-skills](https://github.com/jtydhr88/screenwriting-skills) 는 완전한 영어판을 만들어 본체에 합쳤다가 나중에 지웠고, 그때 결론을 낸 논거가 여기서도 그대로 통합니다 —— 중국어를 못 읽는 사람에게 번역된 한 벌이 있어야 한다면, 영어를 못 읽는 사람에게도 있어야 하고, 그다음은 일본어, 그다음은 한국어, 그다음은 프랑스어입니다. 이 패키지는 31개 파일입니다. 네 언어면 124개가 되고, 각자 따로 어긋나며, 어느 것이 낡았는지 알려 주는 장치는 아무것도 없습니다. 번역 자체는 싼 일입니다. 진짜 대가는 한 번 갈라내고 나면 두 번째 분기를 거절할 떳떳한 근거가 사라진다는 것입니다.

실행 시점에는 이렇게 덮습니다:

- **출력 언어는 질문한 언어를 따릅니다.** 한국어로 물으면 한국어로 옵니다.
- **용어는 원어에 닻을 내립니다.** *object writing*, *prosody*, *family rhyme*, *hook*, モーラ, 符割り, 협음 —— 저본의 중국어 표기 자체가 이미 번역어이므로, 원어를 개념과 함께 들고 다니게 합니다.
- **대응하는 번역어가 없는 용어는 원형 그대로 두고 짧은 주를 붙입니다.** 十三辙, 依字行腔, 類音階, 字余り 는 원형과 한 줄 설명으로 나옵니다.
- **당신의 가사는 그 가사의 언어 그대로입니다.** 광둥어 가사를 영어로 논하는 것은 흔한 일입니다. 바뀌는 것은 대화의 언어이지 원고가 아닙니다.

이렇게 해서 내주는 것은 감사 가능성（auditability）입니다. 중국어를 읽지 못하면 지시 파일 자체는 읽을 수 없고, agent 가 그것에 대해 전해 주는 말만 읽게 됩니다. **이것은 실제로 치르는 대가입니다.** 그리고 번역된 한 벌이 정말로 사 올 수 있는 것도 딱 그 하나입니다. 모든 규칙이 확인 가능한 출처와 쪽수를 달고 있다는 데에 가치 전부가 걸려 있는 라이브러리에게, 그 하나는 네 갈래를 영구히 유지하는 부담만큼의 값어치는 없습니다.

**README 는 다른 문제**이고, 이쪽은 번역합니다. 짧고, 내용이 안정적이며, 새로 온 사람이 가장 먼저 마주치는 것이기 때문입니다.

## 스킬 구성

여섯 층. **언어층이 이 라이브러리의 줄기**이며, 이것이 따로 설명할 가치가 있는 유일한 설계 결정입니다.

언어가 바뀐다는 것은 같은 방법론에 표 한 장을 갈아 끼우는 일이 아닙니다. 표준중국어는 다른 모든 제약 위에 성조 대 선율이라는 제약을 통째로 하나 더 얹습니다. 광둥어는 한 걸음 더 나아가 **쓰는 순서 자체를 뒤집습니다**——선율을 먼저 확정하면 각 음높이 자리에 쓸 수 있는 성조가 몇 개밖에 남지 않으므로, 단어보다 먼저 성조 골격을 정합니다. 일본어는 음절이 아니라 모라（モーラ, 박）로 셉니다. 영어는 강세에 걸려 있습니다. 이것들은 방법 자체가 다르기 때문에 각각 별개의 skill 이며, 모든 skill 이 "다른 언어층으로 이것을 대신해서는 안 된다"고 명시하고 있습니다.

```
L0 workflow    라우터, 두 갈래 프로세스（곡 먼저／가사 먼저）, LYR-SPEC 계약
L1 general     주제 · 구성 · 이미지 · 압운 · 서술
L2 language    표준중국어 · 광둥어 · 영어 · 일본어          ← 줄기
L3 tradition   중국풍 · 뮤지컬 · 랩
L4 execution   성조-선율 점검 · 백엔드로 컴파일 · AI 냄새 진단
L5 corpus      완성된 가사를 뜯어보기
```

## 편곡 라이브러리와의 인터페이스

이것은 하나의 오디오 라인에서 작사 쪽 절반입니다. 나머지 절반이 [music-composition-skills](https://github.com/jtydhr88/music-composition-skills) 이며, 둘은 한쪽이 다른 쪽에 먹여주는 관계가 아니라 **양방향**으로 결합되어 있습니다.

- **곡이 먼저**: ARR-SPEC 이 단락 표, 마디 수, 감정의 호를 넘겨주고 가사는 그 격자 안에 쓰입니다.
- **가사가 먼저**: 가사가 각 행의 길이와 강세 위치를 돌려주고, 편곡 라이브러리가 거기서 마디 수를 끌어냅니다.

여섯 개의 필드는 양쪽에서 일치해야 합니다. 어느 한쪽 라이브러리가 그중 하나를 바꾸면 다른 쪽도 따라 바꿔야 할 의무가 생깁니다.

## 이 패키지에 들어 있지 않은 것

**한국어（받침과 그것이 노래 부르기에 미치는 영향）와 민요적 서사입니다. 둘 다 아직 저본이 없으며, 이 라이브러리는 저본이 없는 skill 을 쓰지 않습니다** —— 어떤 언어의 운율 규칙을 지어내면 자신만만하게 틀린 답이 나오기 때문입니다. **즉 이 패키지에는 한국어 언어층이 없습니다.** 한국어 가사 요청에는 일반층（주제·구성·이미지·압운·서술）을 쓰고, 언어층은 다루지 않는다고 분명히 말해야 합니다.

저본 목록에는 한국어 음성학 책 네 권（郑政德《韩国语语音入门》, 李翊燮 외《韩国语概论》, 刘小瑛《韩语发音快速入门》,《新魅力韩国语发音入门》）이 들어 있습니다. 언어 제약층은 그 위에 세워지며, 없는 것은 한국어 작사 실무의 저본입니다.

## 체례

- `SKILL.md` frontmatter: `name`（kebab-case, 폴더 이름과 일치）과 "Use when …" 으로 끝나는 비교적 긴 영어 `description`. 중국어 키워드를 덧붙여 두 언어 모두에서 라우팅이 되게 했습니다.
- skill 본문은 중국어이며 번호를 매긴 원칙, 표, 체크리스트로 되어 있습니다. 출력 언어는 질문한 언어를 따릅니다.
- **모든 규칙에는 실패 조건이나 자가 점검 동작이 붙어 있습니다.**
- 저본끼리 견해가 갈리는 곳은 두 입장을 나란히 남기고, 각각이 어떤 경우에 적용되는지 주를 달았습니다.
- **저본이 없는 것은 쓰지 않습니다.** 어떤 skill 의 예시가 책의 것이 아니라 이 라이브러리가 직접 만든 것이라면 그렇게 밝힙니다.
- 인용에는 출처와 쪽수를 답니다.
- 긴 표와 자세한 예시는 `reference.md` 에 두어 `SKILL.md` 를 40 KB 이내로 유지합니다.
- 설계상 agent 중립: skill 파일은 어떤 agent 의 이름도 쓰지 않고 agent 전용 문법도 쓰지 않습니다.
