# lyric-writing-skills（作詞スキル集）

[English](README.md) · [中文版](README_ZH.md) · 日本語 · [한국어](README_KO.md)

作詞のための 17 個の agent skill（[Claude Code](https://docs.anthropic.com/en/docs/claude-code/skills) と [OpenAI Codex](https://developers.openai.com/codex/) 用）。4 言語 29 冊の書籍（英語の作詞教本、中国語の詩律と作詞、広東語の実務、韓国語音声学）に、ソンドハイムが自ら註釈を付けた歌詞全集 2 巻を加えたものから抽出しました。

両方の agent が同じ skill ファイルを共有します。一度入れれば両方で動きます。

**言葉と一緒に、仕様書が一枚できます。** 歌詞を頼むと、agent は LYR-SPEC（詞稿仕様書）を埋めます。中身は、この曲が言う「一つのこと」、誰に向かって言うのか、どの瞬間の話か、全曲を貫く一つの物、各行の音数と強拍位置、押韻の型、意図的な非対称、そして言語層のチェック結果です。改稿のときに突き合わせるのも、同じこの一枚です。

**この library がやること。** 歌詞の良し悪しには判断基準があり、この library はその基準の集まりです。言うことは一つだけにする、写真に撮れる一つの物に落とす、誰が言っているのか、どの瞬間の話かを押さえる、文型そのものに仕事をさせる、韻は最初に思いついたものを取らない。library の関門はすべて、実際の選択を一つ引き出すためにあります。

**自分の言語で訊いてください。** skill 本文は中国語で書かれています。底本の大半が中国語の原著か中国語訳だからです。どの言語で訊いても、agent はその言語で答えます。

**このスキル群は、時間と引き換えに品質を取る仕組みです。** プロの音楽制作ワークフローを一通り回すと、一曲に二十分以上かかることも珍しくありません（agent が判断基準を読み、仕様書を埋め、自己点検を通すため）。その代わりに得られるのは、プロ水準の仕様書です。

**本ライブラリは作品を一切収録していません。作者自身のものも他のアーティストのものも、編曲も歌詞もありません。** 音楽作品の良し悪しは主観的な判断です。ご自身で使い、その価値と、時間という代価をご自身で判断してください。

## このシリーズの四つの library

一本のオーディオ・ラインを、独立した四つの library に切り分けています。それぞれ単独で使え、継ぎ目が明文化されているので組み合わせても使えます。

| Library | 何をするか | 状態 |
|---|---|---|
| **[music-composition-skills](https://github.com/jtydhr88/music-composition-skills)** | 作曲と編曲。ブリーフを ARR-SPEC（編曲仕様書）に変える：調、テンポ、セクション表、和声、誰がいつ入り退くか、エネルギー曲線、ボーカルとミックスの意図 | 公開済み |
| **[lyric-writing-skills](https://github.com/jtydhr88/lyric-writing-skills)** | 作詞。立意の関門を LYR-SPEC に変える：構造、イメージ、韻、叙述、そして中国語（普通話・広東語）、英語、日本語、韓国語の言語層 | **この library** |
| **映画音楽** | 映像に合わせて書く音楽：スポッティング、カットとの関係、cue の書き方と命名、テーマの映画全体での展開 | 予定 |
| **ミキシングとサウンドデザイン** | ミックスの意図を実際の操作に変える：EQ、コンプレッション、リバーブ、オートメーション、マスタリング | 予定 |

**独立している。** 既存のメロディに詞を当てるなら作詞 library だけで足りる。インストゥルメンタルを編曲するなら作編曲 library だけで足りる。

**名前のついた受け渡しで組み合わさる。** ARR-SPEC と LYR-SPEC は六つのフィールドを共有する：セクション id、小節数、セクション名、テンポ、キー、誰が歌うか。先に作った側が決め、後から作る側は読むだけ。曲先なら作曲・編曲の側が決め、詞先なら作詞の側が決める。このときは各行の音数と強勢位置が逆に小節数を縛る。後の側がどれかを変えたいときは先の側にメッセージを送り、相手が変えたら読み直す。詞先ではテンポとキーを空けておき、作曲・編曲の側に決めてもらってよい。ARR-SPEC の中のミックス意図の欄は、ミキシングを担う側に渡すもの。映画音楽を担う側の cue sheet は、作曲・編曲の側に渡すブリーフ。

**継ぎ目は仕様書に書かれている。** どの library も自足しており、単独で入れて使える。skill は他の library の名前を出さず、他の library が入っていることも前提にしない。自分の担当でない問いは、職能の名で誰に渡すかをはっきり言う：EQ とコンプレッションの実務はミキシングへ、スポッティングと cue の執筆は映画音楽へ。library どうしは仕様書だけで受け渡す：対外インターフェースの節に、渡すフィールドと、あれば読む上流のフィールドが並び、さらにどの側も書き込めるメッセージ・チャネルが一本ある。

## なぜこれが要るのか

歌詞を書く agent は、それ自体が言語モデルです。10 秒で 4 連の歌詞を書いてくれます。韻は踏み、字数もそろい、イメージも豊かです。問題は、この library 全体がそのために作られたあの一点です。その 4 連は、どの曲のものでもありうる。

モデルは、あなたが決めなかったところを全部埋めます。そして埋めるのは、それが読んできたすべての平均値です。人が「機械が書いた」と聞き取るのは、まさにそれです。具体的な物を置くべきところに抽象名詞が置かれ、4 つのセクションが同じ長さで、サビが 3 回とも一字一句同じで、感情の弧が痛みから受容へ、そして祝福へときれいに解決し、韻は必ず誰もが最初に思いつく語になる。これは**誰も選択をしなかった音**です。

この skill 群が agent にさせるのは、その選択です。現役の作詞家が下すのと同じやり方で決め、しかも後から突き合わせられる場所に書き出します：この曲が言う一つのこと、誰に向けて言うのか、何分のどの瞬間の話か、繰り返し出てきて出るたび意味がずれていく物はどれか、どの一行が型を破りなぜ破るのか、どの字はその音に乗せてはいけないか（声調が変わって別の単語になってしまうから）。**補うのは、選択という一歩です。**

中国語の歌詞には第二の理由があり、これは趣味の問題ではありません。普通話では字調とメロディが衝突すると、聴き手には別の単語に聞こえます。広東語ではそれは端的に別の単語です。声調を確認せずきれいな一行を書くだけのモデルは、歌った瞬間に崩れる歌詞を出してきます。この種の制約は計算できるものであり、この library はそれを書き留めてある場所です。日本語には語彙を区別する字調の対立はありませんが、同じ種類の計算できる制約が日本語の側にもあります。モーラの数と、ピッチアクセントがメロディとぶつかるかどうかです。それを扱うのが `lw-japanese` です。

手渡すのは、歌手と作曲・編曲の側のための詞稿で、一箇所ごとに理由が付いています。

```
# 「このメロディに詞を付けて、小節数と各行の音数はこれです」

# 「この稿、読む分には問題ないのに何か凡庸で、どこが悪いか言えない」

#   書く順序が逆であり、他のどの言語層も代用できない

#   全体の約 5 分の 1 の字
```

## よくある組み合わせ

見た目より複雑です。一行の brief が作曲・編曲・作詞の三方面で十数個の skill を動かし、エージェントが何を読み何を出すかは、その一行にいくつかの要点が入っているかで決まります。以下は実際に最後まで走らせた組み合わせです。言い方、通る skill、出てくるもの。歌詞のある用例は作曲編曲ライブラリと作詞ライブラリの両方が必要です。

**1. 特定のアーティストの作風で、歌詞付きの曲を書く**（最も多い）

> あるアーティストのある曲のような中国語ポップスを一曲、女性ボーカル、歌詞付きで。

通る：lw-workflow → lw-song-intent → lw-structure → lw-mandarin → lw-tone-check；mc-workflow → mc-style-chinese-pop → mc-melody → mc-development → mc-arrangement-arch → mc-vocal-direction
出る：LYR-SPEC と ARR-SPEC
注：参照アーティストから借りるのは編成・テンポ・ボーカルの人物像・セクションの運びだけ。詞と曲は借りません。

**2. 抖音向けのキャッチーな曲、物語なし**

> 抖音向けのキャッチーな曲を一曲、女性、甘め、物語はなし、歌詞付き。

通る：lw-song-intent（態度型）→ lw-structure（反復予算、フックの位置）→ lw-rhyme → lw-mandarin；mc-style-chinese-pop → mc-rhythm-groove → mc-arrangement-arch
注：「物語はなし」の一言が歌詞の型を決めます。言わなければ既定で情景型になります。

**3. 悲しいラブソング、直接言う、情景なし**

> あるアーティストのある曲のような悲しいラブソング、男性ボーカル、歌詞付き。直接言うタイプで、情景描写はなし。

通る：1 と同じ。ただし lw-song-intent は態度型を通り、錨は一つの文（各サビの頭で繰り返す行）；mc-vocal-direction がオンマイクの男声と最後の一行の余白を担当
注：コーパスでは態度型の曲の四割に、写真に撮れる物が一つもありません。サビは「あなた」に向けた一文、A メロは自分の状態、冒頭は独白。これが欲しければ brief に「直接言う、情景も物もなし」と書きます。

**4. 一つの気分、物語にはしない**

> 中国語ポップスを一曲、三分半、女性ボーカル。テーマは、引っ越しの日に充電ケーブルを壁のコンセントに残したまま、二本先の通りで思い出して、取りに戻らなかったこと。物語にはしないで。思い出して、まあいいかとなる気分が欲しい。

通る：lw-song-intent（情景型、錨の物はケーブル）→ lw-imagery → lw-structure → lw-mandarin → lw-tone-check；曲側は 1 と同じ
注：情景型と物語型の境界はここです。物はあるが、筋は進まない。

**5. インストゥルメンタル、ゼロから作曲**

> 二分四十秒のインスト曲を、ショート動画の BGM に。主奏はナイロン弦ギター、少しのパーカッションとベース、鍵盤一台まで可。雰囲気は「午後三時、人を待っている、急いでいない」。ボーカルなし。

通る：mc-workflow → mc-development（動機、性格、発展の手法）→ mc-melody → mc-form → mc-harmony → mc-rhythm-section → mc-orchestration
出る：ARR-SPEC（主題素材と各セクションの展開手法を埋めたもの）、一枚の説明
注：歌詞がないので作詞ライブラリは関与しません。判定基準は mc-development にあります。新素材は半分未満、再現あり。

**6. 詞と曲は済み、編曲だけ**

> メロディと歌詞が出来ている中国語ラブソングを編曲して。サルサの感じで、ブラス入り、中速からやや速め。仕様書だけ。

通る：mc-workflow（編曲ルート）→ mc-style-latin → mc-rhythm-section → mc-orchestration（ブラス）→ mc-arrangement-arch → mc-texture-layering
出る：ARR-SPEC と一枚の説明のみ

**7. 融合：A メロはラップ、サビは中華風**

> ある曲のようなラップと中華風の曲を、完全な中国語歌詞付きで。

通る：mc-workflow §2.4 スタイル融合 → mc-style-hiphop（ベース）+ mc-style-chinese-pop（オーバーレイ）；lw-rap（A メロ）+ lw-chinese-style（サビ）+ lw-mandarin

**8. 広東語の詞を既存のメロディに**

> このメロディに広東語の詞を付けて。小節数と各行の音数は添付。

通る：lw-workflow（曲先）→ lw-cantonese（まず音高クラスで計算、それから字を選ぶ）→ lw-tone-check
注：広東語は書く順序が逆で、北京語の層では代用できません。

brief の中で実際に効いている文：

| あなたが言うこと | それが決めること |
|---|---|
| アーティスト名＋曲名 | 編成・テンポ・ボーカルの人物像・セクションの運びを借りる。詞と曲は借りない |
| 女声／男声、甘め／オンマイク | mc-vocal-direction の人物像と音域 |
| 物語なし ／ 直接言う情景なし ／ 物語にしない | 歌詞の型：態度型 ／ 物のない態度型 ／ 情景型。言わなければ既定は情景型 |
| 尺 | セクション数と小節数はここから逆算 |
| 成果物リスト | 欲しいファイルを書けば、エージェントはそのリスト通りに出す。一つ欠ければ未完 |

どれもフルで走らせると二十分以上かかります。上の「時間で品質を買う」の項を参照。

## ツールは一切不要

このプラグインは文字だけでできています。入れればそのまま使え、ほかに入れるものはありません。10 項目のチェックはすべて目で判定でき、字調とメロディの衝突チェックにも手作業の方法があり、問題が実際に起きる 3 種類の位置だけを見ます。

**ルールは判定基準です。** 通らなかったら、その行を直すか、なぜこの曲はそれでよいのかを一文書くか、どちらかです。

## 多言語対応

**skill は一組、言語は使うときに出し分けます。** skill は中国語で一度だけ書かれており、どの言語で訊いても agent はその言語で答えます。切り替えのスイッチも、別途のインストールも、言語ごとのプラグインもありません。

**ここは丁寧に分けて書く必要があります。** この library には**言語層**があり、二つの話が混ざりやすいからです。言語層が扱うのは、**歌詞**がどの言語で書かれるかです：普通話の字調、広東語の協音、英語の強勢、日本語のモーラ、韓国語の받침。これから述べる方針が扱うのは、**指示ファイル**がどの言語で書かれているかです。日本の作詞家が日本語で訊けば、日本語の回答と `lw-japanese` 層のすべてが返ってきます。その背後にある指示ファイルが中国語だというだけのことです。**日本語版がなくても、日本語の作詞には対応しています。**

skill 本文を他言語へ分岐させることはしません。これは決定です。姉妹プロジェクトの [screenwriting-skills](https://github.com/jtydhr88/screenwriting-skills) は完全な英語版を作り、本体に統合し、その後で削除しました。そのとき決め手になった論はここでもそのまま通ります。中国語が読めない人に訳された一式が必要なら、英語が読めない人にも必要であり、次は日本語、その次は韓国語、そしてフランス語です。このパックは 31 ファイルです。4 言語なら 124 ファイルになり、それぞれ勝手にずれていき、どれが古くなったのかを教えてくれるものは何もありません。翻訳そのものは安い作業です。本当の代償は、一度分岐させてしまえば二度目の分岐を断る筋の通った理由がなくなることです。

使うときにどう覆うか：

- **出力言語は質問の言語に従います。** 日本語で訊けば日本語で返ってきます。
- **術語は原語に錨を下ろします。** *object writing*、*prosody*、*family rhyme*、*hook*、モーラ、符割り、협음：底本の中国語表記それ自体が訳語なので、原語を概念と一緒に持ち歩かせます。
- **対応する訳語がない術語は、原形のまま短い注を付けます。** 十三辙、依字行腔、類音階、字余り はそのままの形と一行の説明で出てきます。
- **あなたの歌詞は、その歌詞自身の言語のままです。** 広東語の詞を英語で議論するのは普通のことです。切り替わるのは会話の言語だけです。

これで手放すものは**監査可能性**です。中国語が読めないかぎり、あなたは指示ファイルそのものを読めず、agent がそれについて語った内容しか読めません。**これは実在する代償です。** そして訳された一式が本当に買えるものは、それ一つだけでもあります。あらゆる規則が検証可能な出典とページを背負っていることに価値の全部が掛かっている library にとって、それは 4 系統を永久に保守し続ける負担に見合いません。

**README は話が別**で、こちらは翻訳しています。短く、内容が安定しており、新しく来た人が最初に出会うものだからです。

## スキルの構成

6 層。**言語層がこの library の幹**であり、これが唯一、説明する価値のある設計上の決定です。

普通話は他のすべての制約の上に、字調とメロディの制約をまるごと一つ積み増します。広東語はさらに進んで、**書く順序そのものを逆にします**。メロディを先に固定すると、各音高位置で使える声調は数個しか残らないので、言葉より先に声調の骨格を決めます。日本語はモーラ（拍）で数えます。英語は強勢に掛かっています。これらは方法のレベルで違うので、別々の skill になっており、どれも「他の言語層で代用してはならない」と明記しています。

```
L0 workflow    ルーター、2 つのプロセストラック（曲先／詞先）、LYR-SPEC 契約
L1 general     立意 · 構成 · イメージ · 押韻 · 語り
L2 language    普通話 · 広東語 · 英語 · 日本語 · 韓国語   ← 幹
L3 tradition   中国風 · ミュージカル · ラップ
L4 execution   字調とメロディのチェック · AI 臭診断
L5 corpus      完成した歌詞を分解する
```

### L0 入口

## 作曲・編曲とのインターフェース

これは一本のオーディオラインの作詞側の半分です。もう半分は作曲・編曲で、このシリーズでは [music-composition-skills](https://github.com/jtydhr88/music-composition-skills) ですが、仕様書を読める人やツールであれば何でもかまいません。両者は仕様書だけで受け渡し、どちらが先かは工程で決まります。

- **曲先**：作曲・編曲の側がセクション表、小節数、感情の弧を渡し、歌詞はそのグリッドの中に書かれます。
- **詞先**：歌詞が各行の長さと強拍位置を渡し、作曲・編曲の側がそこから小節数を導きます。

両者は 6 つのフィールドを共有します：セクション id、小節数、セクション名、テンポ、キー、誰が歌うか。**先に作った側が決め、後から作る側は読むだけです。** 後の側がどれかを変えたいときは、仕様書のメッセージ・チャネルに先の側あての一件を書き、どのフィールドをなぜ変えたいかを伝えます。先の側が受け入れて自分の仕様書を直したら、後の側が読み直します。詞先では、テンポとキーを空けたままにして作曲・編曲の側に決めてもらってかまいません。

## このパッケージに含まれないもの

民謡的な語り物。まだ底本がなく、この library は底本のない skill を書きません。ある形式の韻律規則をでっち上げれば、自信たっぷりの間違った答えが出てくるからです。そうした依頼には一般層を使い、この層は覆っていないとはっきり言ってください。

## 体例

- 各 skill の冒頭には長めの英語の説明文があり、中国語のキーワードを併記しているので、英語で訊いても中国語で訊いても該当する skill が見つかります。
- skill 本文は中国語。番号を振った原則、表、チェックリストで構成。出力言語は質問の言語に従います。
- **すべてのルールに失効条件か自己点検の動作が付いています。**
- 底本どうしで見解が割れるところは、両方の立場を並べ、それぞれがどんな場合に当てはまるかを注記しています。
- **底本のないものは書きません。** ある skill の例がこの library の自作である場合は、そう明記します。
- 引用には出典とページを付けています。
- 長い表と詳細な例は別の参照ファイルに置き、本体のファイルを短く保っています。
- 設計上 agent 非依存：skill ファイルはどの agent の名前も出さず、agent 固有の構文も使いません。

## 技術メモ

- **skill ファイル**：`SKILL.md` はオープン規格 [agentskills.io](https://agentskills.io) に準拠しています。frontmatter には `name`（kebab-case、フォルダ名と一致）と、"Use when …" で終わる長めの英語の `description` があり、中国語のキーワードを併記して、どちらの言語でもルーティングが効くようにしています。長い表と詳細な例は `reference.md` に置き、`SKILL.md` を 40 KB 以内に保っています。
- **走らせるものはない**：プラグインはテキストファイルだけです。走らせるスクリプトはなく、Python も Node も不要で、lint の工程もありません。10 項目のチェックは仕様では LYR-LINT と呼び、すべて人が判定します。
- **仕様書は YAML ファイル**：用例で出るのは `LYR-SPEC.yaml` と `ARR-SPEC.yaml` です。LYR-SPEC のテンプレート、スキーマ、例は `lw-workflow` フォルダにあります（`LYR-SPEC.template.yaml`、`LYR-SPEC.schema.md`、`example-*.yaml`）。
- **本文で普通の言葉で呼んでいるフィールド**：仕様書のメッセージ・チャネルはトップレベルの `messages`、詞先で空けておくテンポとキーは `null` と書きます（`lw-workflow/LYR-SPEC.schema.md` §3）。ARR-SPEC の中のミックス意図は `mix_intent`、用例 5 の主題素材と各セクションの展開手法は `material` ブロックと各セクションの `development` フィールドです。
