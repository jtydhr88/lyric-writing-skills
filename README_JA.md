# lyric-writing-skills（作詞スキル集）

[English](README.md) · [中文版](README_ZH.md) · 日本語 · [한국어](README_KO.md)

作詞のための 18 個の agent skill（[Claude Code](https://docs.anthropic.com/en/docs/claude-code/skills) と [OpenAI Codex](https://developers.openai.com/codex/) 用）。4 言語 29 冊の書籍——英語の作詞教本、中国語の詩律と作詞、広東語の実務、韓国語音声学——に、ソンドハイムが自ら註釈を付けた歌詞全集 2 巻を加えたものから抽出しました。

`SKILL.md` はオープン規格 [agentskills.io](https://agentskills.io) に準拠し、両方の agent が同じファイルを共有します。一度入れれば両方で動きます。

**出力は言葉だけではなく、仕様書です。** 歌詞を頼むと、agent は LYR-SPEC を埋めます——この曲が言う「一つのこと」、誰に向かって言うのか、どの瞬間の話か、全曲を貫く一つの物、各行の音数と強拍位置、押韻の型、意図的な非対称、そして言語層のチェック結果——それを生成バックエンドへの入力にコンパイルします。改稿のときに突き合わせるのも、同じこの一枚です。

**この library の前提を、はっきり書きます。** AI が書いた歌詞は、言葉が下手なのではありません。**誰も選択をしていない**のです。文法は正しく、韻はきれいに揃い、イメージも豊かな 4 連——しかしその 4 連はどの曲のものでもありうる。機械が書いたと一聴でわかるのは、まさにそこです。この library の関門はすべて、実際の選択を一つ強制するために存在します。

**自分の言語で訊いてください。** skill 本文は中国語で書かれています。底本の大半が中国語の原著か中国語訳だからです。どの言語で訊いても、agent はその言語で答えます。

**このスキル群は生成モデルを速くはしません。時間と引き換えに品質を取る仕組みです。** プロの音楽制作ワークフローを一通り回すと、一曲に二十分以上かかることも珍しくありません（agent が判断基準を読み、仕様書を埋め、自己点検を通すため）。その代わりに得られるのは、数行のプロンプトではなくプロ水準の仕様書です。

**本ライブラリは作品を一切収録していません。作者自身のものも他のアーティストのものも、編曲も歌詞もありません。** 音楽作品の良し悪しは主観的な判断です。ご自身で使い、その価値と、時間という代価をご自身で判断してください。

## このシリーズの四つの library

一本のオーディオ・ラインを、独立した四つの library に切り分けています。それぞれ単独で使え、継ぎ目が明文化されているので組み合わせても使えます。

| Library | 何をするか | 状態 |
|---|---|---|
| **[music-composition-skills](https://github.com/jtydhr88/music-composition-skills)** | 作曲と編曲。ブリーフを ARR-SPEC に変える：調、テンポ、セクション表、和声、誰がいつ入り退くか、エネルギー曲線、ボーカルとミックスの意図。Suno、YuE2、MIDI 向けの入力にコンパイルする | 公開済み |
| **[lyric-writing-skills](https://github.com/jtydhr88/lyric-writing-skills)** | 作詞。立意の関門を LYR-SPEC に変える：構造、イメージ、韻、叙述、そして中国語（普通話・広東語）、英語、日本語、韓国語の言語層 | **この library** |
| **映画音楽** | 映像に合わせて書く音楽：スポッティング、カットとの関係、cue の書き方と命名、テーマの映画全体での展開 | 予定 |
| **ミキシングとサウンドデザイン** | ミックスの意図を実際の操作に変える：EQ、コンプレッション、リバーブ、オートメーション、マスタリング | 予定 |

**独立している。** 既存のメロディに詞を当てるなら作詞 library だけで足りる。インストゥルメンタルを編曲するなら作編曲 library だけで足りる。

**名前のついた受け渡しで組み合わさる。** ARR-SPEC と LYR-SPEC は双方向で、曲先なら セクション表と小節数を渡し、詞先なら 行長と強勢位置を返す。六つのフィールドは両方向で一致しなければならない。ARR-SPEC の中の `mix_intent` は、ミキシング library がブリーフとして受け取るもの。映画音楽 library の cue sheet は、作編曲 library がブリーフとして受け取るもの。

**継ぎ目はすでに書かれている。** すべてのスキルが境界表を持ち、他の library に属する問いは その場で下手に答えずに名前で回される。だから予定中の二つの library はすでに随所で参照されている：EQ とコンプレッションの実務はミキシング library へ、スポッティングと cue の執筆は映画音楽 library へ。

## 生成モデルがあるのに、なぜこれが要るのか

言語モデルは 10 秒で 4 連の歌詞を書いてくれます。韻は踏み、字数もそろい、イメージも豊かです。問題は、この library 全体がそのために作られたあの一点です——その 4 連は、どの曲のものでもありうる。

モデルは、あなたが決めなかったところを全部埋めます。そして埋めるのは、それが読んできたすべての平均値です。人が「機械が書いた」と聞き取るのは、まさにそれです。具体的な物を置くべきところに抽象名詞が置かれ、4 つのセクションが同じ長さで、サビが 3 回とも一字一句同じで、感情の弧が痛みから受容へ、そして祝福へときれいに解決し、韻は必ず誰もが最初に思いつく語になる。これは下手な文章ではありません。**誰も選択をしなかった音**です。

この skill 群が供給するのは、その選択です。現役の作詞家が下すのと同じ水準で決め、しかも後から突き合わせられる場所に書き出します——この曲が言う一つのこと、誰に向けて言うのか、何分のどの瞬間の話か、繰り返し出てきて出るたび意味がずれていく物はどれか、どの一行が型を破りなぜ破るのか、どの字はその音に乗せてはいけないか（声調が変わって別の単語になってしまうから）。**やっているのは、専門家の水準のルールで生成モデルを指揮することです。生成モデルを作り直そうとはしていません。**

中国語の歌詞には第二の理由があり、これは趣味の問題ではありません。普通話では字調とメロディが衝突すると、聴き手には別の単語に聞こえます。広東語ではそれは端的に別の単語です。声調を確認せずきれいな一行を書くだけのモデルは、歌った瞬間に崩れる歌詞を出してきます。この種の制約は計算できるものであり、この library はそれを書き留めてある場所です。日本語には語彙を区別する字調の対立はありませんが、同じ種類の計算できる制約が日本語の側にもあります——モーラの数と、ピッチアクセントがメロディとぶつかるかどうかです。それを扱うのが `lw-japanese` です。

モデルは歌手でありスタジオであり続けます。これはそこへ手渡す詞稿で、一箇所ごとに理由が付いています。

```

git clone https://github.com/jtydhr88/lyric-writing-skills.git
cp -r lyric-writing-skills/plugins/lyric-writing/skills/* ~/.claude/skills/
```

#### プロジェクト単位

```bash
mkdir -p .claude/skills
cp -r lyric-writing-skills/plugins/lyric-writing/skills/* .claude/skills/
```

```bash
codex plugin marketplace add jtydhr88/lyric-writing-skills

```

```
# 「このメロディに詞を付けて——小節数と各行の音数はこれです」
# → lw-workflow（曲先トラック）→ lw-song-intent → lw-structure → lw-mandarin

# 「この稿、読む分には問題ないのに何か凡庸で、どこが悪いか言えない」
# → lw-ai-tell-audit：列挙できる 8 つの機械の指紋、各項目をそれを管轄する skill へ

# 「広東語のメロディに詞を埋めたい」
# → lw-cantonese：まず音高クラス体系で計算し、それから字を選ぶ——広東語は
#   書く順序が逆であり、他のどの言語層も代用できない

# 「この A メロをラップに変えて」
# → lw-rap（押韻密度、多音節韻、中国語ラップへの転用表）

#   ——全体の約 5 分の 1 の字
```

## よくある組み合わせ

見た目より複雑です。一行の brief が作曲・編曲・作詞の三方面で十数個の skill を動かし、エージェントが何を読み何を出すかは、その一行にいくつかの要点が入っているかで決まります。以下は実際に最後まで走らせた組み合わせです。言い方、通る skill、出てくるもの。歌詞のある用例は作曲編曲ライブラリと作詞ライブラリの両方が必要です。

**1. 特定のアーティストの作風で、歌詞付きの曲を書く**（最も多い）

> あるアーティストのある曲のような中国語ポップスを一曲、女性ボーカル、Suno で生成、歌詞付きで。

通る：lw-workflow → lw-song-intent → lw-structure → lw-mandarin → lw-tone-check → lw-suno-interface；mc-workflow → mc-style-chinese-pop → mc-melody → mc-development → mc-arrangement-arch → mc-vocal-direction → mc-render-compile
出る：LYR-SPEC.yaml、ARR-SPEC.yaml、suno-pack.md（タイトル、スタイル記述、セクションタグ付き歌詞、除外語）
注：参照アーティストから借りるのは編成・テンポ・ボーカルの人物像・セクションの運びだけ。詞と曲は借りません。

**2. 抖音向けのキャッチーな曲、物語なし**

> 抖音向けのキャッチーな曲を一曲、女性、甘め、物語はなし。Suno 生成、歌詞付き。

通る：lw-song-intent（態度型）→ lw-structure（反復予算、フックの位置）→ lw-rhyme → lw-mandarin；mc-style-chinese-pop → mc-rhythm-groove → mc-arrangement-arch → mc-render-compile
注：「物語はなし」の一言が歌詞の型を決めます。言わなければ既定で情景型になります。

**3. 悲しいラブソング、直接言う、情景なし**

> あるアーティストのある曲のような悲しいラブソング、男性ボーカル、Suno 生成、歌詞付き。直接言うタイプで、情景描写はなし。

通る：1 と同じ。ただし lw-song-intent は態度型を通り、錨は物ではなく一つの文（各サビの頭で繰り返す行）；mc-vocal-direction がオンマイクの男声と最後の一行の余白を担当
注：コーパスでは態度型の曲の四割に、写真に撮れる物が一つもありません。サビは「あなた」に向けた一文、A メロは自分の状態、冒頭は独白。これが欲しければ brief に「直接言う、情景も物もなし」と書きます。

**4. 一つの気分、物語にはしない**

> 中国語ポップスを一曲、三分半、女性ボーカル。テーマは、引っ越しの日に充電ケーブルを壁のコンセントに残したまま、二本先の通りで思い出して、取りに戻らなかったこと。物語にはしないで。思い出して、まあいいかとなる気分が欲しい。

通る：lw-song-intent（情景型、錨の物はケーブル）→ lw-imagery → lw-structure → lw-mandarin → lw-tone-check；曲側は 1 と同じ
注：情景型と物語型の境界はここです。物はあるが、筋は進まない。

**5. インストゥルメンタル、ゼロから作曲**

> 二分四十秒のインスト曲を、ショート動画の BGM に。主奏はナイロン弦ギター、少しのパーカッションとベース、鍵盤一台まで可。雰囲気は「午後三時、人を待っている、急いでいない」。ボーカルなし。

通る：mc-workflow → mc-development（動機、性格、発展の手法）→ mc-melody → mc-form → mc-harmony → mc-rhythm-section → mc-orchestration → mc-render-compile
出る：ARR-SPEC.yaml（material ブロックと各セクションの development を埋めたもの）、suno-pack.md、一枚の説明
注：歌詞がないので作詞ライブラリは関与しません。判定基準は mc-development にあります。新素材は半分未満、再現あり。

**6. 詞と曲は済み、編曲だけ**

> メロディと歌詞が出来ている中国語ラブソングを編曲して。サルサの感じで、ブラス入り、中速からやや速め。仕様書だけ、Suno プロンプトは不要。

通る：mc-workflow（編曲ルート）→ mc-style-latin → mc-rhythm-section → mc-orchestration（ブラス）→ mc-arrangement-arch → mc-texture-layering
出る：ARR-SPEC.yaml と一枚の説明のみ

**7. 融合：A メロはラップ、サビは中華風**

> ある曲のようなラップと中華風の曲を、完全な中国語歌詞付きで、Suno 用に。

通る：mc-workflow §2.4 スタイル融合 → mc-style-hiphop（ベース）+ mc-style-chinese-pop（オーバーレイ）；lw-rap（A メロ）+ lw-chinese-style（サビ）+ lw-mandarin

**8. 広東語の詞を既存のメロディに**

> このメロディに広東語の詞を付けて。小節数と各行の音数は添付。

通る：lw-workflow（曲先）→ lw-cantonese（まず音高クラスで計算、それから字を選ぶ）→ lw-tone-check
注：広東語は書く順序が逆で、北京語の層では代用できません。

**9. Suno ではなく、ローカルのオープンソースモデル（YuE2）**

> 同じ曲を Suno を通さず、ローカルの YuE2 で生成したい。仕様書を ABC 譜にコンパイルして。

通る：1 と同じ、加えて mc-symbolic-score（ARR-SPEC を ABC にコンパイル。ボーカル線は小文字音名の音域に、w: 歌詞行付き）
注：実験段階です。歌詞が歌われて聞き取れる割合は、スタイルと歌詞を直接渡す方式より今のところ低い。詳細は mc-symbolic-score §6b。

brief の中で実際に効いている文：

| あなたが言うこと | それが決めること |
|---|---|
| アーティスト名＋曲名 | 編成・テンポ・ボーカルの人物像・セクションの運びを借りる。詞と曲は借りない |
| 女声／男声、甘め／オンマイク | mc-vocal-direction の人物像と音域 |
| Suno ／ ローカル YuE2 ／ 仕様書だけ | 出口：suno-pack、ABC 譜、ARR-SPEC のみ |
| 物語なし ／ 直接言う情景なし ／ 物語にしない | 歌詞の型：態度型 ／ 物のない態度型 ／ 情景型。言わなければ既定は情景型 |
| 尺 | セクション数と小節数はここから逆算 |
| 成果物リスト | 欲しいファイルを書けば、エージェントはそのリスト通りに出す。一つ欠ければ未完 |

どれもフルで走らせると二十分以上かかります。上の「時間で品質を買う」の項を参照。

## ツールは一切不要

このプラグインはただのテキストです。走らせるスクリプトはなく、Python も Node も不要、lint の工程もありません。LYR-LINT の 10 項目はすべて目で判定でき、字調とメロディの衝突チェックにも手作業の方法があり、問題が実際に起きる 3 種類の位置だけを見ます。

**ルールは判定基準であって、通さねばならない門ではありません。** 通らなかったら、その行を直すか、なぜこの曲はそれでよいのかを一文書くか、どちらかです。

## 多言語対応

**ソースは一組、言語は実行時に出し分けます。** skill は中国語で一度だけ書かれており、どの言語で訊いても agent はその言語で答えます。切り替えのフラグも、別途のインストールも、言語ごとのプラグインもありません。

**ここは丁寧に分けて書く必要があります。** この library には**言語層**があり、二つの話が混ざりやすいからです。言語層が扱うのは、**歌詞**がどの言語で書かれるかです——普通話の字調、広東語の協音、英語の強勢、日本語のモーラ。これから述べる方針が扱うのは、**指示ファイル**がどの言語で書かれているかです。日本の作詞家が日本語で訊けば、日本語の回答と `lw-japanese` 層のすべてが返ってきます。その背後にある指示ファイルが中国語だというだけのことです。**「日本語版がない」ことは「日本語の作詞に対応していない」ことではありません。**

skill 本文を他言語へ分岐させることはしません。これは手落ちではなく決定です。姉妹プロジェクトの [screenwriting-skills](https://github.com/jtydhr88/screenwriting-skills) は完全な英語版を作り、本体に統合し、その後で削除しました。そのとき決め手になった論はここでもそのまま通ります——中国語が読めない人に訳された一式が必要なら、英語が読めない人にも必要であり、次は日本語、その次は韓国語、そしてフランス語です。このパックは 31 ファイルです。4 言語なら 124 ファイルになり、それぞれ勝手にずれていき、どれが古くなったのかを教えてくれるものは何もありません。翻訳そのものは安い作業です。本当の代償は、一度分岐させてしまえば二度目の分岐を断る筋の通った理由がなくなることです。

実行時にどう覆うか：

- **出力言語は質問の言語に従います。** 日本語で訊けば日本語で返ってきます。
- **術語は原語に錨を下ろします。** *object writing*、*prosody*、*family rhyme*、*hook*、モーラ、符割り、협음——底本の中国語表記それ自体が訳語なので、原語を概念と一緒に持ち歩かせます。
- **対応する訳語がない術語は、原形のまま短い注を付けます。** 十三辙、依字行腔、類音階、字余り はそのままの形と一行の説明で出てきます。
- **あなたの歌詞は、その歌詞自身の言語のままです。** 広東語の詞を英語で議論するのは普通のことです。切り替わるのは会話の言語であって、詞稿ではありません。

これで手放すものは**可読性ではなく監査可能性**です。中国語が読めないかぎり、あなたは指示ファイルそのものを読めず、agent がそれについて語った内容しか読めません。**これは実在する代償です。** そして訳された一式が本当に買えるものは、それ一つだけでもあります。あらゆる規則が検証可能な出典とページを背負っていることに価値の全部が掛かっている library にとって、それは 4 系統を永久に保守し続ける負担に見合いません。

**README は話が別**で、こちらは翻訳しています。短く、内容が安定しており、新しく来た人が最初に出会うものだからです。

## スキルの構成

6 層。**言語層がこの library の幹**であり、これが唯一、説明する価値のある設計上の決定です。

言語が変わるというのは、同じ方法に別の表を一枚差し替えることではありません。普通話は他のすべての制約の上に、字調とメロディの制約をまるごと一つ積み増します。広東語はさらに進んで、**書く順序そのものを逆にします**——メロディを先に固定すると、各音高位置で使える声調は数個しか残らないので、言葉より先に声調の骨格を決めます。日本語は音節ではなくモーラで数えます。英語は強勢に掛かっています。これらは方法のレベルで違うので、別々の skill になっており、どれも「他の言語層で代用してはならない」と明記しています。

```
L0 workflow    ルーター、2 つのプロセストラック（曲先／詞先）、LYR-SPEC 契約
L1 general     立意 · 構成 · イメージ · 押韻 · 語り
L2 language    普通話 · 広東語 · 英語 · 日本語          ← 幹
L3 tradition   中国風 · ミュージカル · ラップ
L4 execution   字調とメロディのチェック · バックエンドへコンパイル · AI 臭診断
L5 corpus      完成した歌詞を分解する
```

### L0 — 入口

| Skill | 何を扱うか |
|---|---|
| `lw-workflow` | ルーター、最初に答える分岐（曲先か詞先か）、それぞれの工程表、library 全体の境界表、LYR-SPEC のスキーマとテンプレート、10 項目のチェック、そして編曲 library との双方向インターフェース |

### L1 — 一般技法（言語非依存）

| Skill | 何を扱うか | 主な底本 |
|---|---|---|
| `lw-song-intent` | **この library で唯一の硬い関門：一行書く前の 5 つの質問。** この曲がどの種類か（態度型・情景型・叙事型・説理型、既定は叙事型ではない）、この曲が言う一つのこと、誰に向けて言うのか、どの瞬間か、全曲を貫く写真に撮れる物が一つ。各質問がそれぞれ特定の失敗を捕まえ、§7 は本当に答えたのか関門を通すために埋めただけなのかを見分けるテスト | この library 自身の設計。Pattison と Davis と突き合わせ済み |
| `lw-structure` | 各セクションの役目と言ってはいけないこと、曲形テンプレート、タイトルとフックの置き場所、行の形がどうやってセクションを「言い終わった」「まだ終わっていない」と感じさせるか、そして完璧な対称がなぜ表計算シートのように読めるのか | Pattison *Essential Guide to Lyric Form*、Sheila Davis、尤静波《流行歌词写作教程》 |
| `lw-imagery` | object writing と七つの感覚、具体名詞と抽象名詞、感覚の配分、イメージを寄せ集めではなく体系にすること、比喩と死んだ比喩 | Pattison *Writing Better Lyrics*、*Without Boundaries*、*Songwriter's Playground* |
| `lw-rhyme` | 押韻は装飾ではなく構造の道具：完全韻と各種の family rhyme がそれぞれ終止感に与える効果、押韻の型、内韻、意外性、意図的に韻を踏まないこと | Pattison *Essential Guide to Rhyming* |
| `lw-narrative` | 誰が、いつ語り、どこまで知っていてよいか：人称と視点、時制のアンカー、書かずに残すこと、そして感情の弧を完全に解決してしまうのがなぜ機械の指紋なのか | Sheila Davis ×2、*Popular Lyric Writing: 10 Steps* |

### L2 — 言語層（幹）

| Skill | 何を扱うか | 主な底本 |
|---|---|---|
| `lw-mandarin` | 字調は音素である——声調を変えれば単語が変わる。十三轍（13 の押韻類）と各々の代表字、寛い韻と狭い韻、平仄および歌詞でどこまで緩めてよいか、顿（フレーズの区切り）こそが中国語の本当のリズム単位であること、歌いやすさ（開口音と閉口音、早口になる並び）、そして中国語ポップスの実務慣行 | 王力《诗词格律》×2、吴颂今《歌词写作十八讲》、李忠勇《歌词写作常识》、张藜《歌诗之路》、洪源《春消息》、尤静波《流行歌词写作教程》 |
| `lw-cantonese` | 九声と協音は**硬い**制約：破れば違和感どころか、歌った瞬間に別の単語になる。字調とメロディの照合を計算可能にする音高クラス体系、自然な音程差の弾力、六声テスト法、そして逆転した執筆順序 | 黄志华《文字声律与粤语歌创作》、《词家有道》香港の作詞家 16 人へのインタビュー集、黄霑《粤语流行曲的发展与兴衰》 |
| `lw-english` | 強勢と拍の関係：語強勢は変えられないが文強勢は動かせる、機能語を強拍に置かないこと、音節ではなく強勢の数を数えること、prosody、行分けとブレスとエンジャンブメント、そして中国語話者が英語詞を書くときに犯す 6 つの誤り | Sheila Davis *Craft of Lyric Writing*、Pattison、*Lyrics: Writing Better Words* |
| `lw-japanese` | 音節ではなくモーラで数える——促音（小さい「っ」）、撥音「ん」、長音がそれぞれ 1 拍を占める。ピッチアクセントとメロディの衝突、符割り（モーラを音符に割り当てる）、分節、意図的な字余りと字足らず、音数が合わないときの 4 通りの直し方、七五調と「日本語らしすぎる」という警報、そして日本語詞に英単語を混ぜるときの鉄則 | 日本式の作詞・ボーカル制作実務、旋律法、pro songmaking |

### L3 — 伝統層

| Skill | 何を扱うか | 主な底本 |
|---|---|---|
| `lw-chinese-style` | ある詞を「ただ古めかしい」ではなく中国風にしているものは何か：語彙のファミリー、名前の付いた 16 種の言葉遊びの手法とそれぞれの失敗条件、イメージがなぜ一つの一貫した世界を成さなければならないか、典故をどこまで深く使ってよいか | 方文山《中国风：歌词里的文字游戏》 |
| `lw-musical-theatre` | 一曲は行動でなければならず、立ち止まりであってはならない。言葉は作詞家ではなく登場人物の口から出たように響かねばならない。ソンドハイムの三原則——すべては明晰さのために。自分自身の欠点の目録。そしてそのうちどれをポップスの歌詞も守るべきかの転用表 | Sondheim *Finishing the Hat*、*Look, I Made a Hat* |
| `lw-rap` | ボーカルがビートのどこに乗るかではなく、言葉そのもの：押韻密度とそれが聞き取りやすさに払わせる代償、多音節韻と曲げた韻、内容の型と行単位の手法、押韻駆動と意味駆動の取捨、そして中国語ラップへの転用表 | Paul Edwards *How to Rap* 1 & 2 |

### L4 — 実行と検証

| Skill | 何を扱うか |
|---|---|
| `lw-tone-check` | 字調とメロディの衝突チェックのやり方と、結果の読み方。出力は**リスク**であって判決ではありません——長い音符、強拍、はっきりした発音のどれもが、警告の付いた字を救えます |
| `lw-suno-interface` | 完成した歌詞をバックエンドの入力にコンパイルする：セクションタグ、書式、既知の挙動と落とし穴 |
| `lw-ai-tell-audit` | 機械が書いた歌詞の、列挙できる 8 つの指紋。一つずつ数え、それぞれを管轄する skill へ回します。加えてもっと厳しいテスト：タイトルと固有名詞を外し、何も知らない人に渡して、この曲が具体的に何の話なのか言わせてみる |

### L5 — 語料

| Skill | 何を扱うか |
|---|---|
| `lw-case-studies` | 完成した歌詞をどう分解するか：この library 自身のフィールドに対応した 12 行の分析表、現役作詞家 3 人が自ら語る方法と彼らの意見が食い違う箇所、通しの分析例、改稿前後の対照 | 姚谦《我们都是有歌的人》、张藜、洪源 |

## 編曲 library とのインターフェース

これは一本のオーディオラインの作詞側の半分です。もう半分が [music-composition-skills](https://github.com/jtydhr88/music-composition-skills) で、両者は片方がもう片方に供給するのではなく、**双方向**に結合しています。

- **曲先**：ARR-SPEC がセクション表、小節数、感情の弧を渡し、歌詞はそのグリッドの中に書かれます。
- **詞先**：歌詞が各行の長さと強拍位置を返し、編曲 library がそこから小節数を導きます。

6 つのフィールドは双方向で一致していなければなりません。どちらかの library がその一つを変えれば、もう一方も追随する義務を負います。

## このパッケージに含まれないもの

韓国語（받침 とそれが歌唱に及ぼす影響）と、民謡的な語り物。どちらもまだ底本がなく、この library は底本のない skill を書きません——ある言語の韻律規則をでっち上げれば、自信たっぷりの間違った答えが出てくるからです。そうした依頼には一般層を使い、言語層は覆っていないとはっきり言ってください。

## 体例

- `SKILL.md` の frontmatter：`name`（kebab-case、フォルダ名と一致）と、"Use when …" で終わる長めの英語の `description`。中国語のキーワードを併記し、どちらの言語でもルーティングが効くようにしています。
- skill 本文は中国語。番号を振った原則、表、チェックリストで構成。出力言語は質問の言語に従います。
- **すべてのルールに失効条件か自己点検の動作が付いています。**
- 底本どうしで見解が割れるところは、両方の立場を並べ、それぞれがどんな場合に当てはまるかを注記しています。
- **底本のないものは書きません。** ある skill の例が書籍のものではなくこの library の自作である場合は、そう明記します。
- 引用には出典とページを付けています。
- 長い表と詳細な例は `reference.md` に置き、`SKILL.md` を 40 KB 以内に保っています。
- 設計上 agent 非依存：skill ファイルはどの agent の名前も出さず、agent 固有の構文も使いません。
